프로젝트 회고: HealthNYou BLE Chat

본 문서는 프로젝트 진행 과정에서의 문제 해결, 습득한 지식, 그리고 현재 남아있는 이슈들을 정리한 회고록입니다.

1. BLE 핵심 개념 정리 (Basic Concepts)

1.1 BLE 광고 (Advertising)의 의미

  • 개념: 상업적 광고가 아니라, Peripheral 기기가 "나 여기 있어요!"라고 자신의 존재를 알리는 무선 신호를 주기적으로 방송(Broadcast)하는 행위입니다.
  • 비유: 캄캄한 광장에서 "HealthNYou(FF01)"라고 적힌 야광 팻말을 들고 서 있는 것과 같습니다. 이 행위를 하지 않으면 Central 기기가 아무리 스캔을 해도 나를 찾을 수 없습니다(투명 인간 상태).
  • 기술적 구성: 우리 앱은 광고 패킷에 다음 두 가지 핵심 정보를 담아 송출합니다.
1. Service UUID (FF01): 우리 앱 사용자임을 증명하는 식별 코드.
2. Local Name: 사람 눈에 보이는 기기 이름 (HealthNYou-Chat).

1.2 GATT 프로필과 UUID (Service vs Characteristic)

  • Service UUID (FF01): "HealthNYou 채팅 서비스"라는 큰 카테고리(방)입니다. 수많은 블루투스 기기 중 우리 앱을 설치한 기기를 식별하는 명찰 역할을 합니다.
  • Characteristic UUID (FF02): 실제 채팅 메시지가 오고 가는 데이터 통로(우편함)입니다. 여기에 데이터를 쓰거나(Write), 데이터 변화를 감지(Notify)하여 실시간 대화를 구현합니다.
  • Base UUID: 0000-1000-8000-00805f9b34fb (Bluetooth SIG 표준)를 기반으로 상위 16비트(FF01, FF02)를 커스텀하여 전용 통신 규격을 구축합니다.

1.3 MTU 협상과 데이터 전송 (Chunking)

  • MTU(Maximum Transmission Unit): BLE 패킷 하나가 실어 나를 수 있는 최대 크기입니다. 기본값은 23 Byte이며, 헤더(3 Byte)를 제외하면 실제로는 20 Byte만 전송 가능합니다.
  • 협상 과정:
1. 연결 직후: 기본값(20 Byte)으로 통신이 시작됩니다.
2. 요청 (Android): gatt.requestMtu(512)를 호출하여 확장을 제안합니다.
3. 합의: 상대방(iOS)이 수락한 크기와 내 크기 중 더 작은 값으로 최종 MTU가 결정됩니다.
  • 전송 전략: 협상된 MTU보다 긴 메시지는 애플리케이션 레벨에서 잘라서(Chunking) 순차적으로 보내야 합니다.

2. 발생했던 문제 및 해결 과정 (Troubleshooting)

2.1 iOS와 Android의 BLE 주소 체계 차이

  • 문제: Android는 MAC 주소를 제공하지만, iOS는 보안상 UUID를 발급함.
  • 해결: 플랫폼 고유 ID를 그대로 사용하여 문자열 형태로 관리하도록 설계함.

2.2 메시지 전송 실패 (iOS → Android)

  • 원인: iOS의 Write With Response 방식과 Android GATT 서버 간의 호환성 문제.
  • 해결: 응답을 기다리지 않는 Write Without Response로 변경함.

2.3 iOS에서 상대방(Android)의 연결 종료 미감지

  • 원인: Android 서비스 종료 시 iOS 델리게이트(didModifyServices) 처리 누락.
  • 해결: 해당 메서드를 구현하여 서비스가 사라지면 즉시 연결을 해제하도록 조치함.

2.4 Android 연결 해제 시 ANR(응답 없음) 및 크래시 (NEW)

  • 문제: 안드로이드에서 채팅방을 나갈 때 앱이 멈추거나 튕기는 현상 발생.
  • 원인: Central/Peripheral 중복 이벤트 발생으로 인한 네이티브 리소스 충돌.
  • 해결: _isProcessingDisconnect 플래그를 도입하여 중복 처리를 방지하고, 광고 재시작 전 1.5초의 지연 시간을 두어 안정성을 확보함.

2.5 BLE MTU (20바이트) 제한으로 인한 메시지 잘림 (NEW)

  • 문제: iOS에서 보낸 긴 메시지가 안드로이드에서 20바이트 이후로 잘림.
  • 원인: BLE 기본 통신 단위(MTU) 제한으로 인한 데이터 절단.
  • 해결: 안드로이드에서 requestMtu(512)를 호출하여 전송 용량을 확장하고, 아이폰 Peripheral 특성 속성에 .writeWithoutResponse를 명시적으로 추가하여 호환성을 높임.

2.6 자기 자신 스캔 및 중복 다이얼로그 (NEW)

  • 문제: 본인이 광고 중인 신호를 본인이 잡아 목록에 뜨고, 연결 시 본인에게 승인창이 뜸.
  • 해결:
1. 세션 ID: 앱 실행 시마다 생성되는 4자리 고유 ID를 광고 이름에 포함하여 스캔 시 필터링.
2. 역할(Role) 기반 분기 처리:
  • 문제: 내가 상대방을 연결하려고 눌렀는데(Central), 내 화면에 "연결을 수락하시겠습니까?"라는 다이얼로그가 뜨는 논리적 오류가 있었습니다. (수락창은 연결을 '당하는' 쪽만 떠야 함)
  • 해결: 네이티브에서 연결 성공 이벤트를 보낼 때 role: "CENTRAL" | "PERIPHERAL" 정보를 함께 실어 보냅니다. Flutter는 이 값을 확인하여 내가 건 연결(Central)이면 다이얼로그 없이 바로 입장하고, 걸려온 연결(Peripheral)일 때만 승인창을 띄우도록 로직을 분리했습니다.

3. 새롭게 알게 된 지식 (Key Learnings)

3.1 iOS의 엄격한 파일 관리 및 '명부(pbxproj)' (NEW)

  • 문제: 소스 코드를 수정해도 앱에 반영되지 않고 로그가 안 나오던 현상.
  • 지식: Xcode는 폴더에 파일이 있다고 자동으로 빌드하지 않음. ios/Runner.xcodeproj/project.pbxproj라는 명부(Manifest)에 파일이 등록되어야만 컴파일 대상이 됨.
  • 교훈: VS Code에서 파일을 새로 만든 경우, 반드시 Xcode UI에서 [Add Files to...]를 통해 명부에 등록해야 함. 이번 프로젝트에서는 안정성을 위해 AppDelegate.swift로 코드를 통합하여 해결함.
